# 玩着记，称号随你起

这里的“成就系统”是一份由宿主 Skill 维护的本地游玩记录。它不设固定徽章清单、等级或解锁阈值；模型读懂实际发生的事情，再给用户起一个好笑的称号。

例如，确实多次选择并完成下单的甜品爱好者，可以被叫作“甜品递归调用者”；经常触发奶蛙大笑，可以叫“笑声编译器常驻”。称号只是有事实基础的玩笑，不是麦当劳官方授予的身份或奖励。

## 可以记什么

| 记录 | 事实依据与边界 |
| --- | --- |
| 成功下单次数 | 实际创建订单成功且有可核对的订单标识；预览、推荐、选餐均不计。待支付只能称已创建，不能称已支付 |
| 同一商品次数或份数 | 依据已核实订单中的商品及数量；可按需要统计出现订单数或累计份数，但展示时说清口径 |
| 挑战成功次数 | 依据本次挑战的真实数值与用户约定目标。热量为约 1024 kcal，允许 ±50 kcal；未达到金额或积分目标的“最接近”结果不能直接称精确达成 |
| 奶蛙触发次数 | `/奶蛙` 确实完成本地大笑后可记录；后续推荐失败不需要抹掉已经发生的大笑 |
| 趣味称号 | 由宿主模型结合实际记录自由发挥，不设固定名单或必须刷到的次数 |

这些只是可选的记录方向，不要求用户按顺序完成，也不要求为了称号消费。用户只想听笑声或看看菜单，同样可以获得适合上下文的趣味称呼；不能虚构其消费记录。

## Skill 与 CLI 各做什么

宿主启用 [SKILL.md](../SKILL.md) 后，灵活使用 CLI 或已授权只读 MCP 查询；真实交易仍在 CLI 中预览和确认。然后根据实际结果，用普通文件工具维护记录：正式记录保存在 `.local/player-state.json`。读读现有记录、补上这次发生的事、起个有趣称号即可，无需调用额外“成就服务”。

`/achievements` 或 `/成就` 负责读取并展示记录文件中的 JSON 内容。纯 Python CLI 不会替模型推理称号，也不会自动统计所有历史订单；没有宿主记录时显示尚无记录。它不是自动徽章解锁引擎。

存储结构按实际协作需要选择。可以使用 `mode`、`order_count`、`food_counts`、`challenge_count`、`laugh_count`、`titles` 等直观名字；这些是建议，不是强制 Schema，不应为了满足模板捏造缺失数值。仅记录真实发生并可核对的结果。

## 简单而可信地维护

- 先读现有记录再更新。同一订单查询多次，只记一次；可在本地保留已计数标识用于去重，公开内容不包含这些标识。
- 如果接口结果不明确或订单仍待核实，先不加成功次数，之后查询确认再补。不会因为网络超时重复发订单来获得次数。
- 记录累计创建订单时，可以顺手注明后来取消的情况；只要不把已取消订单说成已履约，就按用户习惯组织记录。
- 不把一次推荐、购物车或商品详情当作实际购买，也不把未知热量、金额或积分补成想要的目标值。
- `.local/` 被 Git 忽略，记录属于本机私有资料，不承诺云同步或跨设备合并。不要保存 Token、地址、手机号、支付信息或完整接口响应；分享截图也先检查隐私。

成就不会触发领券、下单、兑换或取消，不带奖励，不改变真实麦当劳积分。任何真实写操作仍走“预览 → 明确确认 → 执行”；称号只是让探索过程更有趣。
